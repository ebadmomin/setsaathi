# Gym equipment and reusable workout plans

## Current implementation

The **Gym** page is separate from the Dashboard. It shows the gym name, address, and shared equipment list. A member opens its edit area to report equipment they have seen at that gym. The Dashboard continues to show the membership banner. The gym name comes from that membership. The member can enter the full address manually, or explicitly search OpenStreetMap for the gym and select its exact listing. The UI distinguishes a member-selected listing from an unmatched manual address; a listing match does **not** verify ownership, membership, or that the equipment report is correct. The checklist is grouped into specific strength machines, cardio machines, weights/stations, and training accessories. It includes equipment such as Hip Abductor Machine and Chest Press Machine, while personal items and broad labels such as Walking Shoes, Bodyweight, Machine, Cable, None, and Other are excluded. Each machine choice has a **See image** link that opens Google Images for that equipment name in a new tab, so members can compare pictures before checking the item. Image results can include different models or unrelated products; members should confirm the machine at their own gym.

The selected checklist is stored in the database for the normalized gym name and manual address, or the selected OpenStreetMap object reference. The latter lets two users select the same listing even if they spell the address differently. `GET /api/gyms/equipment` loads that saved list and prechecks it in the editor. `PUT /api/gyms/equipment` replaces the branch's shared list: checking a machine adds it, and unchecking it removes it for everyone at that branch. Changing membership to another gym clears the member's selected address and listing; the former gym's inventory remains saved. This inventory is **member maintained**, not verified by a gym owner. A future owner role should control who can change shared inventory and keep an edit history.

`GET /api/gyms/search?area=...` is a user-triggered server-side Nominatim lookup. It caches repeated searches and limits outbound requests to about one per second on the current single-server deployment. The lookup URL and user agent can be changed with `GYM_LOOKUP_URL` and `GYM_LOOKUP_USER_AGENT`. A short-lived signed selection token is required to save a matched listing, so clients cannot simply submit a fake OpenStreetMap reference. If lookup is unavailable or no listing matches, the member can open OpenStreetMap search directly, then save a full manual address. Equipment image links are generated in the browser and do not call the SetSaathi API. For a scaled deployment, replace the public lookup with a provider or deployment that supports the expected traffic and coordinate the rate limit across instances.

When a branch has been saved, newly generated plans use its shared equipment list; bodyweight exercises remain available. The `equipment_catalog.py` mapping ties exercise records labeled broadly as `Machine`, `Cable`, or `Other` to specific gym assets when the exercise name identifies one. The Exercise Library displays these specific requirements in its cards and instructions. Ambiguous movements are excluded from gym-filtered plans until reviewed. A branch with an empty physical equipment list yields bodyweight plans. Existing weekly and daily plans are saved snapshots and are not silently rewritten when the inventory changes. The personal checklist in Workout Plan remains a fallback when a branch has not been selected, such as for home workouts.

Workout structures and curated exercise candidate pools are versioned in `plan_templates` and seeded from `backend/app/template_catalog.py`. Each template has 24 prebuilt, ordered `plan_variants` in the database. These are reusable blueprints, not complete fixed workouts: the user's gym equipment, level, spine setting, goal, and training days determine which exercises can fill the blueprint. This avoids storing an impractical number of complete plans for every possible combination.

When a member builds a weekly plan, the API randomly orders compatible stored variations, fills one using the exercise library, and compares its **actual exercise roster** with the member's plans from the last 14 days. The roster signature ignores cosmetic exercise ordering, so simply rearranging the same exercises does not count as a fresh plan. The chosen full plan is saved in `workout_plans` for normal page loads; `plan_assignments` stores the chosen template, variation, configuration, full snapshot, signature, and assignment time for rotation history. The current plan created before this feature is also checked during the 14-day window. A new plan is not silently produced on every page view.

The custom **Generate today's plan** flow also selects from stored variations and checks the saved daily sessions from the previous 14 days. **Generate today's plan** from an existing weekly plan deliberately follows that saved weekly plan. If constraints leave no different compatible plan or session, the API reports this instead of repeating the same exercise roster. Within one weekly plan, each exercise name appears at most once.

## Current limitations and next steps

- Manual gym identity still depends on normalized gym name plus address text, so different spellings can split inventory until members select the same listing. No owner verified gym ID exists yet.
- Some exercise records still use broad equipment labels. The mapper resolves specific requirements where the movement name is clear and excludes ambiguous records from gym-filtered plans. Complete editorial review is needed before promising exact machine matching across the entire library.
- Member reports can be stale or incorrect. A future gym owner role can verify and publish an authoritative inventory; that should take precedence over member reports.
- The gym inventory is applied when generating a new plan. A future plan editor could flag specific saved exercises whose equipment has since become unavailable and offer replacements.
- Variation blueprints use curated exercise pools, while the library fills remaining slots after filtering. An editorial review process should add more variation patterns and rank movements by the exact equipment requirements, movement pattern, and goal before these are treated as coach-approved programs.
